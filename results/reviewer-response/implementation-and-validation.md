# 리뷰 대응: 실제 구현과 검증 범위

기준: `go-sdk` 연구용 구현. 비용 비교는 로컬 Hardhat 실험이다. 기존 [Base Sepolia 에스크로 측정](../gas-analysis/gas-analysis.md) 및 [종단 간 검증](../e2e-validation/table3-e2e-scenarios.md)은 별도 자료다. 이번 리뷰 대응에서 Base Sepolia 거래나 새 컨트랙트 배포는 하지 않았다.

## 1. 구현된 결제 구조

1. 백엔드는 DB 세션 ID와 `keccak256(utf8(세션 ID))`로 만든 에스크로 ID를 Go 노드에 전달한다([channelOrchestrator.js](../../smartcity-payment-backend/src/services/channelOrchestrator.js)의 `startSessionAndOpenChannel`, [orchestrator.go](../../go-perun-node/internal/channel/orchestrator.go)의 `StartSessionAndOpen`).
2. Go는 양쪽 자금 배분이 0인 Perun 채널을 연다. 두 번째 참가자는 MetaMask 사용자가 아니라 서버가 생성한 보관형 참가자다. 실제 USDC는 `SmartCityEscrow.userDeposit`과 `operatorDeposit`으로 예치한다([channel.go](../../go-perun-node/internal/channel/channel.go)의 `OpenChannel`, [SmartCityEscrow.sol](../../smartcontract/SmartCityEscrow.sol)). **현재 Perun 채널 개설은 온체인 예치 TX를 만들지 않는다.**
3. 백엔드는 경과한 1분 단위로 청구를 실행하고 Go의 `ChargeUsage`가 Perun appData 요금과 상태 버전·해시를 갱신한다([usageBillingService.js](../../smartcity-payment-backend/src/services/usageBillingService.js), [channel.go](../../go-perun-node/internal/channel/channel.go)). 이 경로에 인증된 실물 기기 텔레메트리 연결은 확인되지 않았다.
4. 종료 시 백엔드는 청구를 중단한다. Go는 최종 상태와 두 Perun 참가자의 서명을 공식 형식으로 내보내고, 백엔드는 이를 에스크로에 전달한다([proof.go](../../go-perun-node/internal/paymentapp/proof.go)의 `Export`). `settleAndRelease`는 요금을 예약하고, 실제 4분 분쟁 기간이 지난 뒤 `claimSettlement`가 USDC를 분배한다. **현재 정상 종료 시 Perun adjudicator를 통한 `ch.Settle()` 거래는 없다.**

## 2. 비용 비교: 무엇을 합산했는가

직접 결제 방식은 매 사용량 갱신마다 MockUSDC를 사용자에서 운영자로 전송한다. 제안 방식의 네 거래는 **Perun 채널 개설·종료 거래가 아니라** 다음의 에스크로 거래다.

| 에스크로 작업 | 함수 | 갱신 1회 실험의 Gas |
|---|---|---:|
| 사용자 예치 | `userDeposit` | 205,188 |
| 운영자 예치 | `operatorDeposit` | 71,443 |
| 최종 증명 검증과 정산 예약 | `settleAndRelease` | 139,866 |
| 분쟁 기간 후 실제 분배 | `claimSettlement` | 120,469 |
| **제안 방식 합계** | **4개 TX** | **536,966** |

두 방식 모두 같은 로컬 Hardhat EVM과 소수점 6자리 MockUSDC를 사용했다. 제안 방식은 저장 공간과 정산 호출을 최적화한 현재 `SmartCityEscrow.sol` 소스로 측정했다. 컨트랙트 배포·발행은 준비 단계로 제외했고, 제안 방식에 필요한 USDC `approve` 거래도 제외했다. 직접 전송에는 `approve`가 필요하지 않으므로 아래 교차점은 **사전 승인이 완료된 경우의 실행 Gas** 기준이다. 중간 Perun 갱신은 최종 증명의 버전과 누적 요금으로 나타냈고, 이 비용 스크립트에서 실제 n번의 채널 갱신을 실행하지는 않았다. 따라서 이 표는 온체인 실행 비용 비교이며 상태 채널 처리량 측정이 아니다. 각 갱신 횟수는 로컬 1회 실행했다.

| 사용량 갱신 횟수 | 직접 전송 TX | 직접 전송 Gas | 직접 전송 추정 L2 실행 수수료(ETH) | 제안 방식 TX | 제안 방식 Gas | 제안 방식 추정 L2 실행 수수료(ETH) |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 34,484 | 0.000000206904 | 4 | 536,966 | 0.000003221796 |
| 5 | 5 | 172,420 | 0.000001034520 | 4 | 537,026 | 0.000003222156 |
| 10 | 10 | 344,840 | 0.000002069040 | 4 | 537,026 | 0.000003222156 |
| 15 | 15 | 517,260 | 0.000003103560 | 4 | 537,026 | 0.000003222156 |
| 16 | 16 | 551,744 | 0.000003310464 | 4 | 537,014 | 0.000003222084 |
| 20 | 20 | 689,680 | 0.000004138080 | 4 | 537,002 | 0.000003222012 |

수수료는 로컬 측정 Gas에 기존 Base Sepolia 실험의 평균 유효 가격인 **0.006 gwei/Gas**를 곱한 추정치다. 새 Base Sepolia 실거래 수수료가 아니며 Base의 L1 데이터 비용을 포함하지 않는다. 실제 USDC와 MockUSDC의 Gas도 다를 수 있다. 분당 1회 온체인 직접 전송을 가정하면 **15회까지는 직접 전송, 16회째(16분)부터는 제안 방식의 누적 Gas가 더 낮다**. 20회에는 직접 전송 689,680 Gas 대비 제안 방식 537,002 Gas로 약 **22.1% 절감**된다. 직접 전송 방식에는 제안 방식의 예치금 보관·지급 대기·환불 경로가 없다. 최적화된 컨트랙트는 아직 Base Sepolia에 배포하지 않았다. [합계 CSV](../payment-cost-comparison/comparison.csv), [작업별 CSV](../payment-cost-comparison/operations.csv), [재현 스크립트](../../smartcontract/scripts/compare-payment-costs.js)에 근거값이 있다.

## 3. 보안 분석을 위한 위협 모델

### 3.1 보호 대상과 보안 목표

보호 대상은 `SmartCityEscrow`가 보관하는 사용자·운영자 USDC, 특정 DB 세션에 연결된 Perun 최종 상태, 그리고 정산·환불 결과다. 분석의 기준점은 **누가 최종 상태에 서명했는가**와 **그 서명이 무엇을 증명하는가**이다. `State.appData`의 요금은 두 Perun 참가자의 서명을 통해 무결성을 얻지만, 실제 이용 시간이나 기기 상태의 진실성을 그 자체로 증명하지는 않는다.

| 보안 목표 | 현재 구현에서 검사하는 조건 | 보장하지 않는 것 |
|---|---|---|
| 증명·세션 결속 | 최종 상태, 두 원본 서명, 예치 시 기록한 채널 ID, 체인·계약·에스크로 ID·사용자 주소·예치금, 요금 상한을 컨트랙트가 확인 | 서명에 참여하지 않은 MetaMask 사용자의 독립적 요금 승인 |
| 정산 금액 무결성 | `settleAndRelease`에는 별도 요금 인자가 없으며, 검증된 appData의 요금만 예약 | 서버가 서명 전에 입력한 사용량·요금의 사실성, 복수의 상충하는 최종 증명 중 최신 버전 판별 |
| 지급 시점·중복 방지 | 예약 직후 USDC를 옮기지 않고 4분 뒤 `claimSettlement`를 허용하며 중복 청구를 차단 | 사용자에게 독립적인 온체인 이의제기 권한 제공 |
| 제한적 장애 복구 | 정산 전에는 마감 시각+1시간 뒤 누구나 `forceRefund` 호출 가능; 예약 후에는 4분 뒤 누구나 지정된 수취인에게 청구 가능 | 서버가 장애 증거를 공정하게 판정하거나 환불 이슈를 등록하도록 강제 |

### 3.2 주체별 권한과 신뢰 경계

아래의 ‘신뢰’는 인물에 대한 평가가 아니라 **어떤 보안 주장에 그 주체의 정직성이 필요한지**를 뜻한다. 동일한 서비스 제공자가 백엔드와 Go 노드를 운영한다면 두 구성요소를 독립된 감시자로 취급할 수 없다.

| 주체 | 실제 통제·권한 | 분석상 지위 |
|---|---|---|
| MetaMask 사용자 | 본인 지갑으로 USDC `approve`·`userDeposit` 거래에 서명하고 공개 함수를 호출할 수 있음. Perun 참가자 서명 키는 보유하지 않음 | 본인 지갑을 가진 악의적 호출자로도 가정한다. **최종 요금에 대한 독립 서명자라는 가정은 하지 않는다.** |
| Node.js 백엔드·DB | 세션 ID·사용량 갱신 시점·요금 입력·증명 전달·환불 사례 평가와 운영자 거래 제출을 담당 | 정상 요금과 환불 판단에는 신뢰가 필요하다. 증명 **전달값만** 변조되는 좁은 공격 모델에서는 Go 서명 키가 안전하다고 따로 가정한다. |
| Go-Perun 운영자 노드 | 설정된 운영자 개인키로 참가자 0의 상태에 서명하고 최종 Params·State·서명을 내보냄 | 제공자가 정직한 경우 공식 상태 전이·서명 구현을 신뢰한다. 제공자가 악의적이면 이 키도 공격자 권한에 포함한다. |
| Go-Perun 보관형 참가자 | Go 서버가 세션마다 키를 생성하고 같은 프로세스의 `LocalBus`에서 제안·갱신을 자동 수락함. MetaMask 사용자와 다른 주소 | 독립적인 사용자 감시자나 서명 동의자로 취급하지 않는다. 제공자/Go 환경이 침해되면 두 번째 서명 키도 영향을 받는다. |
| 운영자 지갑·관리자 | `OPERATOR_ROLE`로 정산 예약·이슈 등록·환불을 제출함. 배포 관리자에게는 `DEFAULT_ADMIN_ROLE` 및 긴급 취소 권한이 있음 | 외부 공격자 모델에서는 키가 안전하다고 가정한다. 운영자 악의 행위는 별도로 분석하며, 관리자 키의 악용과 임의 권한 변경은 현재 실험 범위 밖이다. |
| EVM·USDC·컨트랙트 | 거래 실행, USDC 전송, 온체인 상태·시각·서명 복구를 제공 | 정상적인 EVM 실행·USDC 동작·서명 암호학을 전제로 한다. 체인 재편성, 토큰 결함, 암호 원시 기능의 파괴는 시험하지 않았다. |
| 실물 기기·환불 증거 | 이용·반납·장애 사실을 뒷받침해야 하지만 컨트랙트가 인증된 기기 데이터를 직접 확인하지 않음 | 독립적으로 검증된 oracle로 가정하지 않는다. 백엔드 정책·제출 증거의 진실성은 온체인 증명이 아니다. |

이 구분은 [보관형 참가자 생성·자동 수락](../../go-perun-node/internal/setup/custodial.go), [서버 운영자 키와 `LocalBus` 설정](../../go-perun-node/internal/setup/setup.go), [사용량 갱신](../../go-perun-node/internal/channel/channel.go), [온체인 권한·증명 검증](../../smartcontract/SmartCityEscrow.sol)에 근거한다. 백엔드가 ‘릴레이’라는 표현은 **최종 증명의 ABI·서명을 에스크로에 전달하고 별도 요금을 제출하지 않는 정산 단계**에 한정된다. 세션 계측·요금 입력과 환불 결정까지 무신뢰 릴레이라는 뜻은 아니다.

### 3.3 공격자 능력과 실험 범위

- **M1 외부 호출자/악의적 사용자:** 자신의 지갑과 거래 입력을 통제하지만 운영자 역할, 관리자 역할, 두 Perun 서명 키는 갖지 않는다. 유효 증명을 얻더라도 직접 정산을 제출하거나, 무단 이슈 등록·환불과 조기 청구를 시도할 수 있다.
- **M2 증명 전달 경로의 변조자:** 권한 있는 운영자 거래에 전달될 Params ABI·State ABI·서명 배열을 바꾸거나 과거 증명을 다시 제출할 수 있다고 가정한다. **Go의 두 서명 키를 탈취하거나 새로운 유효 상태에 서명하는 능력은 없다.** 이는 백엔드 전체 장악과 구별한, 증명 무결성 검증용 모델이다.
- **M3 악의적·침해된 서비스 제공자:** 백엔드의 사용량 입력, 운영자 거래 권한, Go 환경과 운영자·보관형 참가자 서명 키를 함께 통제할 수 있다고 가정한다. 사용량보다 큰 요금의 유효한 최종 증명을 만들거나 두 상충하는 최종 증명에 서명하고, 정산·환불 요청을 지연할 수 있다. 이 강한 모델에서 컨트랙트가 보장하는 것은 주로 **예치금 상한·세션 결속·상태별 지급 규칙**이며, 실제 이용량과 최신 상태의 진실성은 아니다.

`userDeposit`의 사용자 지갑 서명은 USDC 예치 승인이지 Perun 요금 상태에 대한 서명이 아니다. 또한 `OPERATOR_ROLE` 검사와 사용자 독립 인증은 별개다. [환불 라우트](../../smartcity-payment-backend/src/routes/refunds.js)에는 사례·세션 검사가 있지만 별도의 인증 미들웨어가 보이지 않고, [공통 요청 검사](../../smartcity-payment-backend/src/middleware/requestValidator.js)는 주로 Content-Type을 확인한다. 따라서 운영자 키를 가진 서버가 대신 거래하는 API의 접근 제어를 온체인 역할 검사만으로 입증했다고 보지 않는다. 해당 API의 실제 악용 가능성은 별도 침투시험을 수행하지 않았다.

## 4. 위협 시나리오 선정과 검증 결과

시나리오는 **증명 입력 → 최종 상태 선택 → 요금 결정 → 예약 후 지급 → 환불·복구**의 각 신뢰 경계에서 자산 이동이나 부당 청구로 이어질 수 있는 공격을 하나씩 확인하도록 구성했다. 결과는 [로컬 Hardhat 컨트랙트 테스트](../../smartcontract/test/stateBoundSettlement.test.js) 14개와 코드 분석에 근거한다. 테스트용 두 서명 키를 직접 사용한 T2·T7은 **악의적 제공자 능력을 가정한 구성 증명**이지 정상 Go 운영 중 발생한 사건이나 Base Sepolia 공격 실측이 아니다.

| 위협 | 공격 주체·선정 이유 | 검증 입력과 관찰 결과 | 판정 범위 |
|---|---|---|---|
| **T1 무단 정산·증명 위조·도메인 혼동** | M1·M2. 역할 검사나 증명 바이트 결속이 빠지면 다른 채널·비최종 상태로 예치금을 정산할 수 있기 때문 | M1 사용자가 유효 증명으로 직접 정산을 제출해도 권한 오류로 거부됐다. 권한 있는 거래에 비최종 상태나 다른 nonce의 채널 증명을 넣으면 `InvalidPerunProof`로 거부되고 에스크로 상태·USDC 잔액이 유지됐다. 체인·계약·사용자·예치금 결속은 코드로도 확인했다. | 테스트는 무단 호출·비최종·다른 채널을 재현했다. 각 도메인 필드의 개별 변조를 모두 실험한 것은 아니다. |
| **T2 과거 상태·상충하는 최종 증명** | M2·M3. 오래된 상태를 제출하면 최신 요금과 다른 정산이 가능하므로 최신성 검사가 필요한지 확인 | 이전 **비최종** 상태는 거부됐다. 반면 같은 채널에 두 키가 서명한 버전 3·4의 **상충하는 최종** 증명을 구성하면, 버전 4가 체인 밖에만 있어도 버전 3이 정산 예약에 수락됐다. 예약 후 버전 4의 재제출은 상태 검사로 거부됐다. | 정상 Go 경로는 최종화 뒤 갱신하지 않는다. 상충하는 최종 증명은 두 서명 키의 이중 서명을 가정한 강한 공격이며, 현재 에스크로는 더 최신의 체인 밖 상태를 판별하지 못한다. |
| **T3 요금 바꿔치기** | M2. 백엔드 전달자가 서명 후 appData 요금만 바꾸거나 임의 금액을 제출할 수 있는지 확인 | 한 요금에 대한 Params·State와 다른 요금에 대한 서명을 섞어 제출하자 `InvalidPerunProof`로 거부됐다. `settleAndRelease`에는 별도 요금 인자가 없고, 거부 시 USDC가 이동하지 않았다. | **서명 키가 안전한 M2에서만** 요금 바꿔치기를 막는다. 두 키를 통제하는 M3의 허위 요금까지 막는다는 뜻은 아니다. |
| **T4 조기·중복 지급** | M1·M3. 정산 예약이 곧 실제 지급으로 오인되거나 분쟁 기간이 무시될 위험을 확인 | 예약 직후 청구는 `ClaimPeriodNotEnded`로 거부되고 USDC가 에스크로에 남았다. 4분 경과 후 정해진 사용자·운영자에게 지급됐으며 두 번째 청구는 `SettlementAlreadyClaimed`로 거부됐다. | 4분은 **지급 대기 시간**이다. 이 시간만으로 사용자가 독립적으로 이의를 제기하거나 최신 Perun 상태를 제출할 권한이 생기지는 않는다. |
| **T5 무단·과다 환불** | M1 및 운영자. 환불이 자산을 이동시키므로 호출 권한, 선행 이슈, 지급 상한을 확인 | 일반 사용자의 이슈 등록과 이슈 없는 환불은 거부됐다. 정산 전 양수 `refundFare`, 정산 후 검증된 요금을 초과한 `refundFare`도 거부됐다. 정상 이슈에서는 전액·부분 환불과 잔액을 확인했다. | 권한 있는 운영자는 기기 증거 없이 이슈를 등록할 수 있고 사용자는 온체인에서 독자적으로 등록할 수 없다. 환불 판단의 공정성은 온체인 보장이 아니다. |
| **T6 증명 미제공·서비스 중단** | M3 또는 장애. 최종 증명이 없어도 예치금이 영구히 잠기는지 확인 | 정산 예약이 없을 때 마감 시각+1시간 이후 누구나 `forceRefund`를 호출해 두 예치금을 원래 소유자에게 돌려주었고, 만료 전 호출은 거부됐다. 예약 후에는 분쟁 기간이 끝나면 누구나 `claimSettlement`를 호출할 수 있다. | 시간·상태 조건을 충족한 경우의 복구다. 거짓 사용량 청구나 운영자의 환불 거부를 독립적으로 판정하지는 않는다. |
| **T7 제공자 공모·허위 사용량** | M3. MetaMask 사용자가 Perun 상태에 서명하지 않는 구조에서 두 서버 서명이 실제 사용량을 대체할 수 있는지 확인 | 테스트가 두 Perun 키로 사용량 증거와 무관한 2.50 USDC 요금(3 USDC 예치금 이하)의 최종 증명을 구성하자 컨트랙트가 이를 검증하고 정산을 **예약**했다. 사용자에게서 즉시 지급된 것은 아니다. | 서명·세션 결속은 성립하지만 이용 사실은 증명하지 않는다. 이는 정상 Go 갱신 경로가 아니라 두 키를 통제한 악의적 제공자 가정의 한계 재현이다. |

T2에서 비교 대상인 더 높은 버전이 온체인에 등록되지 않았다는 점이 중요하다. [Perun Ethereum 컨트랙트 설명](https://github.com/hyperledger-labs/perun-eth-contracts#dispute)에 따르면 adjudicator 분쟁 경로에서는 상태 등록 뒤 다른 참가자가 **제한 시간 안에** 더 높은 버전으로 반박할 수 있다. 반면 현재 `channel.go`의 `InitiateDispute`는 오류를 반환하고 정상 종료에서 `ch.Settle()`을 호출하지 않으며, `SmartCityEscrow`는 adjudicator의 판정 상태를 정산 조건으로 읽지 않는다. 두 번째 참가자도 서버 보관형이므로 독립적인 반박 주체가 아니다. 따라서 표준 Perun의 가능한 반박 절차를 **현재 USDC 정산의 최신성 보장**으로 계산하지 않았다. 연결하려면 독립적으로 최신 증명을 보관·제출할 참가자, adjudicator 경로, 에스크로의 판정 결과 확인과 분쟁 기간을 함께 설계해야 한다.

T3와 T7은 서로 모순되지 않는다. **공격자가 서명 키를 갖지 못한 경우**에는 전달 도중 요금을 바꾸면 서명 검증이 실패한다. **제공자가 두 키로 새 상태에 서명할 수 있는 경우**에는 잘못된 이용량에서 출발한 요금이라도 예치금 이내의 유효 증명이 될 수 있다. T4·T5의 분쟁 기간도 사용자에게 직접 이슈 등록 권한을 주지 않는다. 제공자가 환불을 거부하면 사용자는 해당 기간만으로 온체인 환불을 강제할 수 없다는 점을 보안 주장에 명시한다.

## 5. 최종 상태 검증 절차

| 단계 | 파일·함수 | 실제 검사 |
|---|---|---|
| 최종 증명 내보내기 | `go-perun-node/internal/channel/channel.go`의 `ExportFinal`, `internal/paymentapp/proof.go`의 `Export` | 저장 채널 복원, `CurrentTX()`, `IsFinal`, 채널 ID, 두 원본 서명 검증, 공식 Params·State 인코딩 |
| 증명 전달 | `smartcity-payment-backend/src/services/channelOrchestrator.js`의 `endSessionAndSettle`, `escrowPayoutService.js`의 `settleAndReleaseInternal` | 청구 중단, 증명 형식 검사, `verifiedFare` 호출; 별도의 요금 인자를 정산 함수에 주지 않음 |
| 채널·상태 검사 | `smartcontract/SmartCityEscrow.sol`의 `verifiedFare` | ABI 정규 인코딩, 예치 시 결속한 채널 ID, 컨트랙트 주소, ledger·non-virtual 플래그, 최종 플래그, `version > 0` |
| 서명 검사 | 같은 함수 | 서로 다른 참가자 주소 2개, 저장된 운영자 주소, 두 Ethereum 서명 복원값 검사. 두 번째는 MetaMask 주소가 아니라 보관형 참가자 주소 |
| 요금 결속 검사 | 같은 함수 | 한 자산·두 명의 0잔액 Perun 배분, appData의 에스크로 ID·체인 ID·계약 주소·저장된 MetaMask 사용자·예치금·요금 상한 검사 |
| 정산 예약 | `settleAndRelease` | 운영자 권한, `FullyFunded`, 예치 마감 시각 경과 후 검증된 요금 저장; 상태 해시·버전 이벤트 기록 |
| 최종 분배 | `claimSettlement` | `Released`, 미청구, `claimableAfter` 경과 확인 후 USDC 전송 |

컨트랙트가 기록하는 상태 해시·버전은 **감사 기록**이지 별도로 저장된 최신 최종 해시·버전과의 비교가 아니다. 채널 ID는 예치 시 정한 채널의 동일성을 확인한다. Params의 nonce는 채널 ID에 반영되지만 최신 상태 버전을 나타내지 않는다. 요금도 증명 검증 **후** 저장하므로 사전에 독립적으로 확정된 예상 요금과 비교하지 않는다.

## 6. 장애 판단과 환불 절차

현재 구현에는 인증된 실물 기기 상태가 백엔드에 자동 보고되고 장애가 자동 확정되는 전체 경로가 없다. 정상 과금은 시간 기반 스케줄러에서 시작한다. 장애 사례는 [환불 API](../../smartcity-payment-backend/src/routes/refunds.js)의 사유 및 선택적 증거 제출, 규칙 평가 또는 수동 검토로 시작한다.

[환불 판단 코드](../../smartcity-payment-backend/src/services/refundDecisionEngine.js)는 `sensor_failure`에 제출된 반납·종료 기록과 요금 기록을 요구한다. `double_charge`는 DB nonce 중복을 조회한다. `unlock_failure`는 독립 증거 확인 없이 자동 승인 대상이며, `service_outage`는 장애 기록 없이도 승인할 수 있다. `device_fault`와 `wrong_charge`는 수동 검토 대상이다. 조건에 해당하는 5 USDC 이하 사례는 자동 승인한다. 이 규칙은 **신뢰하는 백엔드의 정책**이지 기기 증거의 온체인 검증이 아니다.

지급 API는 `APPROVED` 상태와 사례·세션 사용자 일치를 확인한다. [escrowPayoutService.js](../../smartcity-payment-backend/src/services/escrowPayoutService.js)의 `refundToBuyer`는 운영자 지갑으로 `RefundIssue`를 등록하고 요금 인자 0을 전달해 사용자 예치금 전액을 환불한다. 승인된 사례의 금액을 부분 환불액으로 온체인에 전달하지 않는다. 컨트랙트는 운영자 권한, 에스크로 상태, 이슈 존재, 예약 후 분쟁 기간을 검사하지만 기기 증거와 사례 판단 자체는 검사하지 않는다. 환불 라우트에서 콘텐츠 형식·입력값 검사 이상의 인증 미들웨어는 확인되지 않았다.

별도로 최종 Perun 증명이 예치 마감 후 1시간 동안 없으면 [index.js](../../smartcity-payment-backend/src/index.js)와 [settlementRecovery.js](../../smartcity-payment-backend/src/services/settlementRecovery.js)가 `forceRefund`를 실행한다. 이는 기기 장애 탐지가 아니라 증명 생성 실패 복구다.

## 7. 논문에 사용할 수 있는 문단

**비용:** 같은 로컬 EVM과 ERC-20 모의 토큰으로 사용량 갱신마다 직접 결제하는 방식과 제안 방식을 비교하였다. 직접 결제 방식의 온체인 거래 수는 갱신 횟수에 비례하지만, 제안 방식의 온체인 거래는 사용자·운영자 예치, 최종 증명 검증과 정산 예약, 분쟁 기간 후 청구의 4건으로 일정하였다. 사전 `approve` 비용을 제외한 1회 갱신 기준 제안 방식은 536,966 Gas였으며, 분당 1회 직접 전송하는 조건에서는 16회째부터 누적 Gas가 더 낮았다. 20회에서는 직접 전송 689,680 Gas와 제안 방식 537,002 Gas로 약 22.1% 절감되었다. 이 값은 최적화된 컨트랙트의 로컬 MockUSDC 측정 결과로, 실제 USDC와 Base Sepolia에서의 절감률은 별도 검증이 필요하다. 직접 전송에는 제안 방식의 예치금 보관·지급 대기·환불 경로가 없다.

**위협 모델:** 보호 대상은 에스크로에 예치된 USDC와 세션별 최종 정산 결과다. 외부 호출자와 증명 전달값을 변조하는 공격자는 운영자 역할과 Perun 서명 키를 갖지 않는다고 가정한다. 별도의 강한 공격 모델에서는 서비스 제공자가 백엔드의 사용량 입력과 운영자 권한, Go 서버의 운영자·보관형 참가자 서명 키를 통제한다고 가정한다. MetaMask 사용자는 예치 거래에만 서명하며 두 번째 Perun 참가자는 서버가 생성한 보관형 계정이므로, 최종 상태에 대한 사용자 독립 서명을 전제로 하지 않는다. EVM·USDC·서명 암호학과 관리자 권한의 정직성은 실험 범위에서 가정하고, 실물 기기 정보는 인증된 온체인 증거로 취급하지 않는다.

**보안 검증:** 서명 키가 안전한 조건에서 비최종 상태, 다른 채널의 증명, 서명 후 요금이 바뀐 증명은 거부됐고 USDC 잔액은 유지됐다. `SmartCityEscrow`는 예치된 채널 ID와 최종 플래그, 두 Perun 서명, 체인·계약·세션·사용자·예치금에 결속된 appData를 확인한 뒤 그 안의 요금만 예약한다. 정산 직후 지급은 4분간 차단되며, 기간 경과 후 지정된 수취인에게 한 번만 지급됐다. 무단 환불·검증 요금 초과 환불은 거부됐고, 증명 미제공 시에는 마감 시각+1시간 뒤 공개 `forceRefund` 경로로 예치금을 반환할 수 있었다.

**보장 범위의 한계:** 두 서버 서명 키를 통제하는 제공자가 사용량 증거와 무관한 요금에 서명한 경우, 컨트랙트는 예치금 범위의 증명을 수락해 정산을 예약했다. 같은 채널의 상충하는 최종 증명 중 최신본이 체인 밖에만 있으면 더 낮은 버전도 수락된다. 현재 Perun adjudicator의 반박·판정 경로는 USDC 에스크로 정산에 연결되어 있지 않다. 환불 이슈 등록도 운영자 권한에 의존하므로 4분 대기 기간 자체가 사용자 독립 분쟁권을 뜻하지 않는다. 따라서 검증된 것은 **제출된 서명 상태에 대한 결속·지급 규칙**이며, 실제 이용량·최신 상태·환불 판단의 독립적 공정성은 별도 과제로 남는다.

**장애·환불:** 현재 장애 및 과금 오류 판단은 신뢰하는 백엔드의 환불 사례 접수, 정책 평가와 수동 검토를 통해 수행된다. 승인된 사례에 대해 운영자 권한으로 `RefundIssue`를 등록하고 사용자 예치금을 환불한다. 기기 텔레메트리의 독립 인증과 자동 장애 탐지는 구현되어 있지 않다.

## 8. 재현 명령과 변경 파일

Windows PowerShell의 저장소 루트에서 실행한다.

```powershell
cd smartcontract
npm.cmd test
npx.cmd hardhat run scripts/compare-payment-costs.js --network hardhat
cd ..\smartcity-payment-backend
npm.cmd test
cd ..\go-perun-node
go test ./...
```

| 파일 | 변경 목적 |
|---|---|
| `smartcontract/SmartCityEscrow.sol` | 중복 정산 금액 저장 제거, 기한 저장 공간 압축, 중복 이벤트 제거, 운영자 송금 합치기 |
| `smartcontract/scripts/compare-payment-costs.js` | 최적화된 에스크로와 직접 전송의 로컬 Gas·수수료를 15·16회 구간까지 측정 |
| `results/payment-cost-comparison/comparison.csv`, `operations.csv`, `comparison.md` | 합계·작업별 값과 논문용 표 저장 |
| `smartcontract/test/stateBoundSettlement.test.js` | T1~T7의 방어·한계와 청구·환불·긴급 취소 검증 |
| `smartcity-payment-backend/src/services/db.js` | 실제 4분 분쟁 기간과 주석 일치 |
| `go-perun-node/internal/channel/channel.go` | 실제 채널 개설·종료 및 분쟁 경로에 맞게 설명 주석 정정 |
| 이 문서 | 측정 범위, 보장·비보장 항목, 신뢰 가정과 논문 문안 정리 |

비용 스크립트에는 로컬 Node 의존성과 Go가 필요하다. Base RPC, 개인키, MetaMask는 필요하지 않다. 실제 Base Sepolia 직접 결제 비교는 별도의 지갑 자금과 네트워크 설정이 있어야 하며 이번 실행에는 포함되지 않았다.
